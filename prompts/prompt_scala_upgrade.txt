I have an existing Scala pipeline running on DBR 13.3 LTS that I need to upgrade to DBR 16.4 LTS while keeping it in Scala.

## Mode Selection

This prompt supports two modes. Choose one:

### Mode A: Full Assessment + Migration
Run the complete assessment first, present findings for review, then apply approved changes.

### Mode B: Apply from Existing Report
Skip the assessment. I will provide a list of changes to apply from a previously generated assessment report.

If I specify a job ID without a mode, default to Mode A.

## Mode A: Full Assessment + Migration

### Step 1: Assess the Pipeline

Run the assessment from resource 19 (comprehensive-job-assessment.md) against the job. For each notebook in the pipeline:
- Scan for all ANSI compliance issues (Checks 10-22)
- Scan for deprecated/removed configs (Check 28)
- Scan for unsupported operations (Checks 23-27)
- Scan for performance anti-patterns (Checks 37-42)
- Check all output tables for data compatibility (resource 17)

Produce the structured assessment report with every finding, organized by severity (CRITICAL, HIGH, MEDIUM, LOW).

### Step 2: Present Findings for Review

Present the findings in a clear table:

```
ASSESSMENT: <job_name> (<job_id>)
Path: A (Scala 13.3 to Scala 16.4)

CRITICAL (will break on 16.4):
  [ ] C1: Cell 5, Line 12 - CAST(claim_date AS TIMESTAMP) on dirty data -> TRY_CAST
  [ ] C2: Cell 8, Line 3  - spark.sql.ansi.enabled = false -> remove, fix code
  [ ] C3: Cell 12, Line 7 - billed_amount / line_count -> TRY_DIVIDE (zero divisor)
  ...

HIGH (likely to break):
  [ ] H1: Cell 3, Line 1  - spark.databricks.delta.retentionDurationCheck.enabled -> remove
  [ ] H2: Cell 15, Line 4 - .cache() -> remove
  ...

MEDIUM (may cause issues):
  [ ] M1: Cell 20, Line 9 - SELECT * -> use explicit column list
  ...

LOW (performance/informational):
  [ ] L1: Cell 10, Line 5 - .count() > 0 -> .first() is not None
  ...

TABLE FINDINGS:
  claims_bronze: LOW risk
  claims_silver: MEDIUM risk (BOOLEAN columns)
  claims_gold_summary: LOW risk

Which findings do you want me to apply? Options:
  - "all" - apply everything
  - "critical and high" - apply CRITICAL + HIGH only
  - "critical only" - apply only CRITICAL
  - List specific IDs: "C1, C2, C3, H1, H2, M1"
  - "all except L1, M1" - apply everything except specific items
```

Wait for my response before proceeding.

### Step 3: Record Baseline

Before making any changes, record the current Delta table versions for all output tables:

```sql
DESCRIBE HISTORY <schema>.<table> LIMIT 1;
```

Save the version numbers for time travel comparison later.

### Step 4: Create Staging Copies

Create copies of all Scala notebooks in the pipeline into a staging folder:
`/Workspace/Migration/staging/<job_name>/`

Do NOT modify the originals.

### Step 5: Apply Approved Changes

Apply ONLY the changes I approved in Step 2. For each approved change:

1. Navigate to the exact cell/line in the staging copy
2. Apply the fix from the assessment report
3. Log what was changed

Key rules:
- **Do NOT set spark.sql.ansi.enabled = false.** Fix the code with ANSI-safe patterns instead.
- **Do NOT change the language** - keep everything in Scala
- **Do NOT refactor or optimize** beyond what was approved
- Reference `resources/07-ansi-compliance-reference.md` for ANSI fix patterns
- Reference `resources/01-scala-13.3-to-scala-16.4.md` for DBR upgrade patterns
- Reference `skills/dbr_upgrade/skill.md` for the upgrade workflow

### Step 6: Generate Change Manifest

Produce the change manifest showing exactly what was changed:

```
CHANGE MANIFEST: <job_name>
Applied: <count> of <total> findings

Notebook: <name>
  Cell <N>, Line <N>:
    BEFORE: <exact original code>
    AFTER:  <exact new code>
    Reason: <finding ID> - <description>
    Status: APPLIED

  Cell <N>, Line <N>:
    Reason: <finding ID> - <description>
    Status: SKIPPED (not approved)
```

### Step 7: Run and Validate

Run the upgraded notebooks on a DBR 16.4 LTS cluster. Then apply the `conversion_validator` skill in time travel mode:

For each output table:
1. Load the baseline version (from Step 3) using VERSION AS OF
2. Load the current version (written by the upgraded pipeline)
3. Run ALL validation checks (1-14 from conversion_validator skill)

### Step 8: Generate Conversion Report

Apply the `conversion_report` skill. Compare original vs upgraded notebooks and generate:
1. Executive summary with change counts by category
2. Notebook-by-notebook diff with every change documented
3. ANSI compliance audit
4. Risk summary ranked by severity
5. Validation results cross-referenced with code changes

### Step 9: Print Summary

Print:
- Which findings were applied vs skipped
- Validation results (pass/fail per table per check)
- Conversion report executive summary
- Any validation failures correlated with specific code changes
